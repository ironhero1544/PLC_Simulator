# 래더 컴파일 → 모니터/배선 모드 통합 검증

2026-10-01. CSV 가져오기 검증은 실행하지 않았다.

`application_runtime_tests`는 앱의 모든 소스를 실제로 링크하고
`Application::Initialize()`를 실행한다. 편집기에서 사용하는
`ProgrammingMode::CompileLadderToOpenPLC()`로 아래 래더를 컴파일한다.
접점은 0열, 출력은 11열이고 가운데는 수평 연결선인 12열 래더다.

```text
X0 ─────────────────────── (Y0)
X1 ─────────────────────── (Y1)
X0 ─────────────────────── [OUT T0 K2]
T0 ─────────────────────── (Y2)
END
```

## 실제 모니터 실행 경로

`UpdateWithPlcState(false)`가 편집기 실행기로 스캔한다.
X0 ON 후 Y0 ON, T0 200ms 완료 및 Y2 ON을 확인했다.
접점과 코일의 `isActive`, 표시용 타이머 완료 상태도 확인했다.
X0 OFF 후 Y0/Y2 및 코일 표시가 해제된다.

## 실제 배선 모드 경로

앱의 레이아웃 로더로 PLC, 전원, 버튼, FRL, 밸브, 실린더,
리미트 스위치, 타워 램프와 11개 전기/공압 배선을 만든다.
RUN 준비와 앱의 `Application::Update()`를 실행한다.
기본 설정의 고급 물리 계산도 켜 둔다.

테스트는 버튼의 실제 접점 상태만 변경하며 X/Y를 직접 설정하지 않는다.

```text
버튼 접점 → 전기 배선 → X0 → 컴파일된 Y0
→ 솔레노이드 → 공압 배선 → 실린더 전진
→ Box2D 리미트 스위치 감지 → 전기 배선 → X1
→ 컴파일된 Y1 → 배선된 타워 램프 점등
→ 외부 PLC를 관찰하는 모니터의 접점/코일 활성 표시
```

버튼 해제 후 Y0 OFF, 실린더 복귀, X1/Y1 OFF를 확인했다.
이 과정을 10회 반복했다. 실린더 전진 위치는 145 이상,
복귀 위치는 1 미만이어야 한다. 정상 스트로크 끝은 160이다.

스캔 스케줄의 시간만 테스트에서 일정하게 진행시킨다.
전기 배선 계산, 공압 계산, PLC 스캔, 센서 감지, 장치 상태,
모니터 상태 동기화는 앱의 실제 함수이며 테스트용 물리식이나
PLC 결과값으로 대체하지 않는다.

## 발견한 오류와 수정

기존 `CompiledPLCExecutor::SetDeviceState("X…", state)`는 입력 이미지에만
썼다. 앱의 모니터/전기 배선 코드는 이 API를 사용하는데, 다음 스캔의
`RefreshInputs()`가 별도 물리 입력 버퍼의 이전 값으로 덮어썼다.
그 결과 X0 표시가 ON이어도 실행기의 X0/Y0은 OFF였고 T0도 진행되지 않았다.

X 주소 설정을 `SetInput()`으로 전달하여 물리 입력 버퍼와 입력 이미지를
함께 갱신하도록 수정했다. 수정 전 앱 모니터 검사는 실패했고,
수정 후 모니터와 실제 배선 동작 검사가 통과했다.

## 재현과 범위

`BUILD_MAIN_APP=ON`, `BUILD_TESTING=ON`에서
`application_runtime_tests`를 빌드한다.

```text
ctest --test-dir cmake-build-release-mingw -R ^application_runtime$ --output-on-failure
```

이 테스트는 실제 앱 초기화와 앱 실행 경로를 사용하므로 창 생성 가능한
Windows/OpenGL 환경과 저장소의 resources가 필요하다.
명령 실행 디렉터리는 저장소 루트다. CTest가 해당 디렉터리를 지정한다.

Computer-use로 편집 화면의 F5/F7 입력과 F4 컴파일도 실행했다.
다만 이전 시작 오류 창과 글꼴 표시 문제 때문에 화면만으로 전체 배선
시나리오를 판정하지 않았다. 위 합격 결과는 실제 앱 실행 경로의
통합 테스트에 따른 결과다. GUI 픽셀 색상이나 클릭 동작의 전수 검증,
외부 PLC 하드웨어, 모든 FX 명령 조합의 검증을 의미하지 않는다.
